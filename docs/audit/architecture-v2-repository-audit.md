# Architecture V2 Repository Audit

Audit date: 2026-09-15
Branch: `refactor/architecture-v2`
Scope: repository root, all applications, packages, Flyway history, security, API consumers, infrastructure, CI, tests, and existing audit material.

## Executive assessment

Koupreng is a substantial working monorepo, not a blank-slate rebuild. Its strongest foundations are the separate user/admin applications, centralized frontend HTTP clients, Flyway-managed schema, server-side ownership checks, DTO-based controllers, payment review/idempotency protections, OpenAPI tooling, CI, and 189 passing backend tests. Those parts should be preserved.

The principal V2 problem is backend cohesion. The 279 production Java files are arranged mainly by technical type: 25 controllers, 38 service files, 24 repositories, 35 entities, and 113 DTOs. A feature change therefore crosses several broad packages and can accidentally couple unrelated domains. The correct migration is a feature-by-feature modular-monolith strangler, not a rewrite.

The repository is not production-ready yet. A previously exposed Telegram credential remains an external release blocker until the owner rotates/revokes it and completes the documented history procedure. Other high-priority gaps are incomplete paid-subscription fulfillment, organization roles that do not yet authorize downstream domain actions, cookie-authentication CSRF behavior without end-to-end browser coverage, and guest-contact uniqueness that is not enforced atomically by MySQL.

## Application audit

### Backend

Current flow is generally `controller -> service -> repository -> entity`, with DTOs at the HTTP boundary and transactions in services. The implementation includes authentication, users, organizations, templates, invitations, public invitation access, sections/customization, media, guests, RSVP/wishes, delivery, seating, check-in, budget, gifts, notifications, template payments, subscription packages, dashboards/reports, admin operations, audit logs, and an optional local AI stub.

What works and should remain stable:

- controllers return DTOs or response envelopes rather than entities;
- ownership/scoped repository lookups protect invitation children;
- Spring Security enforces admin routes on the server;
- important seating, check-in, RSVP, and payment writes use transactions and locking where already implemented;
- Actuator, Prometheus, structured request logging, upload validation, and rate limiting exist;
- provider-specific payment verification is mostly behind services/adapters;
- OpenAPI is generated by springdoc, with production UIs disabled by default.

Architectural problems:

- broad type packages obscure domain ownership and create high fan-in services;
- `InvitationService`, `AdminManagementService`, and notification/payment services coordinate many repositories;
- old and canonical route families coexist (`/api/auth`, `/api/users/me`, `/api/admin`, `/api/v1/**`);
- `TemplateOrder`, `TemplatePaymentOrder`, and the invitation-gift `PaymentTransaction` family are easy to confuse;
- the `waf` package mixes application abuse filtering with terminology normally reserved for an edge WAF;
- several list/report APIs are unbounded;
- checked-in OpenAPI can drift from runtime annotations without a contract-diff gate.

### Frontend user

The user application already follows a useful `app/pages/features/shared` shape. Routing is split by marketing, authentication, host, and builder/public routes. HTTP access is centralized under `shared/api`, and most domain calls live under `features/<feature>/api`.

Preserve the UI, Khmer typography, templates, animation behavior, builder, responsive work, and route aliases. Refactor candidates are duplicate API/service names (for example media, delivery, template, and payment clients), a few large feature files, mixed persisted/unsaved event concepts, and inconsistent partial-error presentation. No frontend migration should begin until the corresponding backend contract is stable.

### Frontend admin

The admin app is correctly independent and has an application-level admin guard plus server-side `ROLE_ADMIN` enforcement. Its HTTP client is centralized, and the old `lib/api.js` is only a compatibility re-export. The app has less test depth than the user app (three source tests at audit time), so later admin work must add authorization, error, and critical-page coverage before structural cleanup.

### Telegram and payment integration

The Telegram service is an adapter: it recognizes trusted ABA notification messages and calls an internal Spring endpoint with a server secret. The backend validates order code, amount, currency, status, and expiry. Detection defaults to `PAID_PENDING_REVIEW`; entitlement is not granted until trusted confirmation. Row locking and uniqueness constraints support idempotency.

Remaining risks are retention of raw provider/Telegram metadata, a remote PayWay verification call inside a database transaction, multiple overlapping payment model families, and incomplete paid-subscription fulfillment. Telegram must not become the owner of payment state.

## Database and Flyway audit

Flyway contains V1 and V3-V16; the missing V2 is historical and must not be backfilled. V1 creates authentication. V3 establishes templates, invitations and children, planning, subscriptions, audit, and gift/payment tables. V4-V5 complete invitation/guest/RSVP/media fields. V6-V9 add template payment orders and ABA/Telegram fields. V10 adds delivery. V11-V13 add planning, profiles, organizations, seating/check-in, account recovery, packages, notifications, and system audit. V14-V16 seed and consolidate templates.

Strengths:

- migrations are forward-only and production does not use Hibernate schema creation;
- important opaque tokens, slugs, order codes, transaction IDs, entitlements, seats, check-ins, and organization membership have constraints/indexes;
- invitation child tables use explicit foreign keys and mostly appropriate cascades;
- monetary columns use decimal types.

Risks and follow-ups:

- local `spring.flyway.out-of-order=true` is inherited by production unless explicitly overridden;
- production currently uses `ddl-auto=none`, which avoids mutation but does not validate entity/schema drift;
- nullable/un-normalized guest email and phone are not protected by invitation-scoped database uniqueness;
- legacy payment/audit/event table families require evidence before consolidation;
- callback/raw-message JSON needs a retention/redaction policy;
- a clean MySQL migration test exists but remains environment-dependent outside CI.

No existing migration may be edited. Every V2 schema adjustment must be a new migration and must be tested both from an empty schema and from the current V16 state.

## Authentication and security audit

Implemented controls include BCrypt password hashing, signed JWTs, issuer/expiry checks, active-user and token-version validation, server-side roles, Google and Telegram identity verification, CORS allowlists, optional secure HttpOnly cookies, security headers, request throttles, upload MIME/extension/signature checks, ownership authorization, sanitized exceptions, constant-time internal-secret comparison, and production secret validation.

Open items by severity:

| Severity | Finding | Required disposition |
| --- | --- | --- |
| BLOCKER | Historical Telegram credential exposure | Owner must revoke/rotate, prove old-token rejection, update deployments, and complete the documented history procedure. |
| HIGH | Paid subscription has no complete trusted payment-to-entitlement transition | Design an idempotent subscription order and transactional activation flow. |
| HIGH | Organization role labels do not authorize downstream actions | Introduce an explicit permission matrix and policy service before enabling team operations. |
| HIGH | Cookie JWT mode has conditional CSRF protection but no end-to-end browser proof | Test token issuance/header handling, missing or invalid tokens, hostile origins, logout, and every intentionally ignored route. |
| HIGH | Guest contact uniqueness is service-only | Define normalization, repair duplicates, add additive MySQL constraints, map conflicts. |
| MEDIUM | PayWay verification holds a DB transaction open | Verify externally, then enter a short locked transaction and re-check state. |
| MEDIUM | Raw payment/provider metadata retention is undefined | Minimize, redact, authorize, and expire data. |
| MEDIUM | Unbounded collections and exports | Add backward-compatible bounded pagination/filtering. |
| MEDIUM | Application `waf` terminology/responsibility is unclear | Retain protections, then move abuse controls under security; leave edge WAF to Cloudflare. |

## Deployment and infrastructure audit

Nginx, Prometheus, firewall, backup, least-privilege MySQL, and Cloudflare tunnel references exist. CI runs backend tests/static analysis, frontend lint/test/build/dependency analysis, bot tests, secret scanning, a clean-MySQL migration job, browser smoke tests, vulnerability audits, and deployment-config validation.

Production container delivery is incomplete because no Dockerfiles or Compose definition are tracked. Nginx currently focuses on the API and must later be reconciled with the independent user/admin SPA route strategy. Redis is justified only for the existing production rate-limit backend; it must remain optional for local development.

| Classification | Current artifacts | V2 action |
| --- | --- | --- |
| KEEP | app boundaries, frontend visual design, Flyway history, DTO HTTP boundaries, security/ownership tests, centralized HTTP clients, OpenAPI tooling, CI, Telegram review-first behavior | Preserve behavior and strengthen tests. |

## Recommended migration map

1. Establish `shared/exception`, `shared/response`, configuration profile isolation, architecture rules, and a stable error contract.
2. Move auth/security and user/account code together; keep current routes as adapters while adding canonical `/api/v1` routes.
3. Move template catalog and entitlement code, then invitations/customization/sections/media.
4. Move guests, RSVP, check-in, seating, delivery, planning, and reporting with ownership-policy tests.
5. Consolidate the payment domain behind provider/verifier ports; complete subscription fulfillment separately.
6. Move notifications, admin, audit, and organization permission policy.
7. Stabilize runtime OpenAPI and add a contract-diff gate.
8. Migrate user consumers, run responsive/accessibility QA, then migrate admin consumers.
9. Clean Telegram/payment adapters, add containers/Nginx/Compose, finish CI/security review, then remove verified legacy code.

Each slice must keep routes and JSON stable, pass its focused tests plus the full backend suite, update OpenAPI/docs, and record any deferred deletion.

## Phase 1 and Phase 2 decision record

Current state: a reliable layered backend with broad packages and workstation `.env` imported by the base configuration.
Problems: domain ownership is implicit; shared exceptions live in a generic package; test/production profiles can see local configuration.
Target state: a modular monolith whose feature modules depend on a small shared kernel and whose local `.env` import is dev-only.
Affected first slice: `shared/exception`, `shared/response`, `shared/i18n`, controller OpenAPI imports, and Spring profile configuration.
Strategy: introduce canonical V2 types, migrate all backend callers atomically, preserve the serialized error contract, isolate the dev profile, run focused and full suites. No compatibility bridge was needed because the complete caller migration was small and verified.
Risks: duplicate advice beans, exception type not being caught, OpenAPI schema rename, or local startup losing `.env`; tests and the dev-only configuration file cover these risks.

## Guest contact integrity slice decision record

Problem: invitation-scoped duplicate email/phone checks occurred before writes and could race under concurrent requests.
Implementation: append-only V17 adds generated normalized email/phone columns and named invitation-scoped unique constraints in one atomic `ALTER TABLE`. Existing application checks remain for early feedback; transaction-commit constraint violations map to `GUEST_DUPLICATE`, while unrelated integrity exceptions return a sanitized `DATA_CONFLICT`.
Data policy: email normalization is lowercase plus outer trim; phone normalization is outer trim; blank contacts become `NULL`. No guest row is rewritten or deleted.
Release gate: the documented read-only duplicate audit and a real-MySQL fresh/upgrade/concurrency run are required before production deployment. The local integration test remains skipped without the explicitly configured MySQL test environment. Verification: 215 tests passed, 0 failed, 1 skipped; SpotBugs and PMD reported no findings.

## Subscription payment fulfillment slice decision record

Problem: paid subscription rows were created and shown in payment history, but only template orders had a confirmation/fulfillment path; the admin UI consequently sent subscription order codes to a template-only endpoint.
Implementation: a typed ADMIN-only `/api/v1/admin/payments/confirm` dispatcher under `payment/api` and `payment/application` now routes `TEMPLATE` and `SUBSCRIPTION` to separate policies. Subscription fulfillment pessimistically locks the order, verifies server-owned amount/currency and pending state, records durable confirmation evidence, replaces the prior active subscription, activates the purchased duration, emits an audit event, and returns an idempotent paid result on retry. The previous template-only endpoint remains compatible.
Concurrency: append-only V18 adds payment evidence fields plus a generated-key unique constraint allowing at most one active subscription per user. Constraint races return `SUBSCRIPTION_ACTIVATION_CONFLICT` without database details.
Consumer: the admin payment page now supplies the history row's `itemType` to the unified endpoint; routes and presentation remain unchanged.
Release gate: run the documented active-subscription duplicate query plus fresh-schema, upgrade, and concurrent-confirmation tests against credentialed MySQL before deployment. Automated provider fulfillment remains deferred until its signed callback/evidence contract is approved. Verification: 227 backend tests passed, 0 failed, 1 skipped; SpotBugs and PMD reported no findings. The admin consumer's 10 tests and production build also passed.
