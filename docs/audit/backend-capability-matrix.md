# Backend capability matrix

> **Historical discovery snapshot (2026-08-10):** this matrix supported migration planning. Current implementation/evidence is tracked in `current-gap-status.md` and `../qa/verification-results.md`.

Audit date: 2026-08-10

The Spring Boot application is the persistence and authorization authority. `apps/frontend-user`, `apps/frontend-admin`, and `apps/telegram-bot` are consumers; browser storage is not a source of business truth.

## Cross-cutting architecture

- Runtime: Java 25, Spring Boot 4.0.7, Spring MVC, Spring Security resource server, Spring Data JPA, Flyway, Redis-backed production rate limiting, MySQL/PostgreSQL runtime drivers.
- Security chain: security headers -> WAF -> authentication throttling -> public RSVP throttling -> internal-payment secret filter -> bearer/cookie JWT authentication -> request logging.
- API envelope: success responses use `ApiResponse<T>`. Errors now include `timestamp`, numeric `status`, stable `code`, safe `message`, `path`, and `fieldErrors`; the legacy validation `fields` key remains during migration.
- Data authority: JPA/Flyway state is authoritative. Frontend caches, session storage, and route state may optimize UX but cannot create entitlements, permissions, RSVP, check-in, seating, or payment truth.

## Schema observations

- Migrations are append-only from `V1`, `V3` through `V16`; the missing `V2` is harmless, while local `spring.flyway.out-of-order=true` is a documented operational risk.
- Both legacy payment tables (`payment_transactions`, `payment_webhook_logs`, `telegram_notifications`, `template_orders`) and current template-payment tables exist. This is evolutionary duplication, not justification for an in-place migration rewrite.
- Existing foreign keys and unique constraints cover core identity, one RSVP/check-in/seat assignment relationships, and order/transaction identifiers. Normalized invitation-scoped guest email/phone uniqueness is presently enforced in service code only.
